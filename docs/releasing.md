## 递增规则

- 新功能交付递增对应组件的小版本，修复已交付版本的问题递增补丁版本；破坏性变更须单独说明迁移和兼容范围。
- 若尚未产出候选包，围绕同一次交付的功能与修复可以汇总到同一候选版本；版本号不是提交计数器。
- 每次交付源码不同的新 IPA 递增 build；相同源码提交重试工作流可保持原 build。应用关于页应能区分不同交付包。
- 只改文档或工作流且未改变交付内容时，不机械递增运行时版本。API 增加筛选能力时递增 API，Web 没有对应改动时保留原版本。
- 在根 `CHANGELOG.md` 中先写候选记录，列出用户可见变化、兼容要求与来源提交。历史验收文档中的旧版本作为当时记录保留，不做全文替换。

## 提交与交付检查

1. 核对 `git status --short`，仅暂存当前任务的改动。
2. 核对版本来源、锁文件和变更记录是否一致。版本元数据与文档调整只需做对应格式、引用和一致性检查，不为此运行耗时业务测试。
3. 按 `GEMINI.md` 使用中文 Conventional Commit：精确 scope、Header 后空行及 Body 的 `- ` 清单。说明动机、组件/数据流、体验或维护收益，以及实际验证与兼容边界；避免为凑格式虚构界面收益。
4. 提交后检查 `%s` 和 `%b`，确认消息包含 Body，再按用户授权推送。
5. 用户要求发布时分别触发 `build-ios.yml` / `deploy.yml`。仅标注实际观察到的结果；工作流受理不等于构建或部署成功。用户要求不等待时，返回运行链接及待确认状态。
6. 发布记录或验收记录保留源码 SHA、版本、Actions 链接与实际状态；真机验证单独记录。需要正式 Git tag / Release 时，按用户明确的发布要求创建，避免把候选元数据标成已发布版本。
