# 原章节增补与改写

在管理后台打开一本已有正文的作品，在 AI 创作对话里直接说「在第十二章她开门之前，补一句写她犹豫的描写」。可以用章名、章号、原文或剧情指明位置。Agent 会查找对话起点及之前的章节，读取原文后提交建议。如果定位结果有歧义，会请你确认要改的那一处。

建议生成后，可从对话里的产出链接查看目标章节和前后对照。继续说「这版再自然一点」，Agent 会基于同一选段继续调整。说「把这一版写回原章」会在对话中准备确认卡，核对并点击「确认写回原章节」后才会更新读者看到的正文。

Web 统一通过 Agent 对话发起增补与改写，输入区不再提供独立的「改写原章节」入口。需要精确指定原文时，在消息里提供章名或章号并引用要改的段落；需要修改整章时直接说明。生成后也可在产出详情点击「预览写回原章」。单次选区最多 6000 个 Unicode 字符，长章节可分段修改。

章节 ID、目录位置、来源链接保留，选区外的原始内容原样保留，正文变化沿用数据库触发器使旧摘要失效。版本指纹包含章节 ID、标题、目录位置和完整正文；生成、预览、确认和恢复都核对当前版本。发生冲突时重新读取原文，不能用旧建议覆盖新内容。

每次实际写回都会保存独立的章节修改历史，历史与恢复接口继续保留。恢复前须预览并确认目标版本，恢复本身也记录历史，可以再次恢复。删除创作对话或清理生成任务不会删除这些章节版本；删除对应章节或作品时历史随之删除。存在后续编辑的历史不允许直接覆盖当前章节。

## 接口与存储

- GET /api/ai/agent/sessions/:id/chapters/:chapterId：读取当前会话可编辑范围内的原文及版本。
- GET /api/ai/agent/sessions/:id/chapters/:chapterId/history?offset=0：分页读取实际保存历史，每页 20 项。
- POST /api/ai/writing/chapter-edits：提交章节 ID、会话 ID、版本、UTF-16 选区、逐字选段、要求和幂等请求 ID。可指定文本模型预设；继续调整时传 previousTaskId。
- 现有 Agent 操作接口增加 apply_chapter_edit 和 restore_chapter；确认仍只接收已保存的操作 ID，不能在确认请求中替换建议正文。
- 迁移 086_ai_agent_chapter_edits.sql 增加持久历史表，并扩展操作类型。正文、历史、操作回执和完成事件在同一个事务内保存。

API/Web 需要配套更新。iOS 源码已接入章节建议展示、写回与恢复确认；旧客户端无法识别新增的操作类型，需要更新客户端后使用。原生构建与真机验收另行记录。
